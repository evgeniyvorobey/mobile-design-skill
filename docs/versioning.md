# Versioning

The skill follows [Semantic Versioning 2.0.0](https://semver.org/) with adjustments for a prompt-and-documentation artifact.

---

## Version components

`MAJOR.MINOR.PATCH`

### MAJOR — breaking contract change

Bump when any of the following changes in a way that breaks existing integrations:

- Mode set (adding, removing, renaming a primary mode)
- Output contract (required sections, field names, section order)
- `SKILL.md` frontmatter schema (`name`, `description`, or new required keys)
- `skill/metadata.yaml` schema
- Directory layout that external tools rely on
- Command or invocation syntax (`/mobile-design-skill`)
- Removal of a guardrail

### MINOR — additive enhancement

Bump when:

- A new guardrail, principle, or quality bar is added
- A new document is added under `docs/` that other parts of the skill reference
- A new sub-case within an existing mode (for example, Mode D1–D4)
- A new optional field in a template
- Source hierarchy is extended with a new family
- Evals criteria are extended

MINOR changes must not break existing responses generated by earlier versions against the same input.

### PATCH — non-behavioral fix

Bump when:

- Documentation typo or clarification that does not change behavior
- Link repair
- Example refinement without structural change
- Internal script fix (validator, bump script, CI)
- Frontmatter text polish

---

## Single source of truth

`skill/metadata.yaml` holds the canonical version.

All other version references are derived from it:

- `SKILL.md` frontmatter `version:` field
- `.claude/skills/mobile-design-skill/SKILL.md` frontmatter `version:` field
- `README.md` version badge
- `CHANGELOG.md` latest header
- Git tag `vX.Y.Z`

---

## How to bump

Use the bump script. Manual edits risk drift between files.

```bash
python3 scripts/bump_version.py patch   # 1.3.0 -> 1.3.1
python3 scripts/bump_version.py minor   # 1.3.0 -> 1.4.0
python3 scripts/bump_version.py major   # 1.3.0 -> 2.0.0
python3 scripts/bump_version.py 1.5.2   # explicit
python3 scripts/bump_version.py --show  # print current version
```

The script:

1. Reads the current version from `skill/metadata.yaml`.
2. Computes the new version.
3. Updates `skill/metadata.yaml`, both `SKILL.md` frontmatters, and the README badge.
4. Inserts an `## [Unreleased]` placeholder at the top of `CHANGELOG.md`.
5. Prints the remaining manual steps.

After running the script:

1. Fill in the `## [Unreleased]` placeholder with real `### Added`, `### Changed`, `### Fixed`, `### Removed` entries, then rename its heading to `## [X.Y.Z] - YYYY-MM-DD`. The placeholder is deliberately unversioned: `validate_release.py` rejects a non-semver top heading, an empty top entry, and a version heading that appears twice, so a placeholder cannot be tagged as a release.
2. Run `python3 scripts/validate_repo.py`.
3. Run `python3 scripts/validate_release.py --tag-or-ref vX.Y.Z`.
4. Commit the changes.
5. Tag: `git tag vX.Y.Z`.
6. Push: `git push && git push --tags`.

## Release checklist

Before tagging a release:

- [ ] Version bumped via `scripts/bump_version.py`
- [ ] CHANGELOG entry written with real content, not placeholder
- [ ] `scripts/validate_repo.py` passes
- [ ] `scripts/validate_release.py --tag-or-ref vX.Y.Z` passes before tagging
- [ ] Examples regenerated against the new version if they reference version-bound behavior
- [ ] Evals reviewed against the new version's structural checks if the output contract changed
- [ ] No uncommitted changes outside the bump diff

After tagging:

- [ ] `git push --tags` performed
- [ ] GitHub release notes written (for MAJOR and MINOR; optional for PATCH)

---

## Version history policy

- Every MAJOR and MINOR release gets a tag and a CHANGELOG entry.
- PATCH releases get a CHANGELOG entry; tagging is optional but recommended.
- Never force-push to main once a tag exists on a commit; tags are immutable references.
- Never retroactively edit a CHANGELOG entry for a released version; add corrections in a new entry.

---

## Pre-release and experimental versions

For experimental changes, use a suffix:

```
1.4.0-alpha.1
1.4.0-beta.1
1.4.0-rc.1
```

Pre-release versions are not the default install target. Document the experimental scope in the CHANGELOG entry.

---

## Compatibility expectations

- **Same MAJOR version**: a skill client using version `X.Y.Z` can safely load any `X.*.*` release without changing how it invokes the skill.
- **New MINOR version**: may add new optional sections to outputs. Clients that parse output must tolerate unknown sections.
- **New PATCH version**: no behavioral change; safe to upgrade without review.
- **New MAJOR version**: requires a review of the client's invocation and parsing logic.
